# Saved lineups and automatic results

Each new structured recommendation is archived in `fantaapp_lineup_history`, independently of the team's latest recommendation. Its key is `(team_id, season, matchday, method)`; DeepSeek, Kimi, Statistical engine, ChatGPT and Federico have separate entries. Regeneration or manual saving replaces only the matching entry and clears its previous actual result. Seasons and matchdays remain separate. Removing a team removes its archive.

The archive captures the roster, Fantacalcio player identities, ordered bench, rules, generation timestamp, round deadline and full recommendation. Workspace saves and archival updates are a single PostgreSQL statement, with the existing revision check. Ordinary edits and follow-up questions do not replace archived choices. Actual-score updates are guarded by the recommendation ID and source retrieval time, preventing stale requests from attaching results to regenerated choices.

The latest compatible existing recommendation is migrated on initialization. Earlier overwritten suggestions cannot be recovered. Stale recommendations whose original roster/research cannot be established are not reconstructed from the current team.

## Manual choices

ChatGPT and Federico use an editable pitch with all supported modules, role-filtered available roster players and an ordered bench. Assigned players are excluded from every picker across starters and bench. Clear their occupied slot before selecting them elsewhere; empty bench slots are omitted when saved. Module changes preserve choices, promote the first reserves for added positions and place surplus starters at the front of the bench. Selecting any of the five methods queries its own archived choice for the current season and matchday; a missing entry shows an empty pitch. Save manual edits before switching, as selecting a method reloads its database entry. Saving is explicit and uses the same guarded database/archive operation as generated recommendations, including the selected module, starters, bench and optional notes.

Method selection is read-only: it does not replace the team's latest recommendation or module in the database. The selected archive's module, roster, starters, bench, explanation and player predictions are displayed together. Saved AI choices remain visible with a warning when research expires or the current roster changes. Loading failures show a retry action and an empty pitch; cancelled or superseded requests cannot update the current selection. Module preview changes are local and reset on method selection. Model follow-ups remain available for the team's latest compatible recommendation; other archived suggestions are readable without sending a question against a different method's result.

ChatGPT's Copy prompt button uses the same shared request builder as DeepSeek and Kimi, joining its exact instructions and input strings. It makes no model request. A selectable text preview provides a fallback when clipboard access fails. The user pastes this prompt into their own chat, then pastes the returned JSON into Risposta di ChatGPT and clicks Importa formazione, or enters the lineup manually. Import accepts plain JSON, Markdown code blocks and triple-quote wrappers, up to 100,000 characters. It validates the module, roster IDs, availability, duplicate assignments and starter role counts before replacing the draft. Invalid imports preserve all current choices. Bench priority within each role and existing notes are preserved; extra forecast/analysis fields are ignored. The pasted response is temporary editor state, not stored in the database. Import does not save: the user can edit the populated pitch and bench before explicitly saving the ChatGPT entry to Confronto. If the research or roster changes after copying, the prompt must be copied again before saving. Editing and import work without fresh research; copying and saving require the same fresh verified season/matchday context used by the other methods. Manual entries contain no invented forecast or app model cost and cannot use model follow-up questions.

## Results

`GET /api/lineups?teamId=…` returns compact history summaries. Adding `season` and `matchday` returns that round's full entries. `POST /api/lineups` with those three fields collects actual matchday results and saves calculated scores. The Confronto page does this automatically when opened; Aggiorna risultati also rechecks results. There is no background scheduler. A warm function caches fetched votes for five minutes.

The current team listone selects the actual-vote provider: FantaMaster for `fantamaster`, Redazione Fantacalcio for `leghe` (and legacy teams without a listone). The Leghe collector reads the public Fantacalcio matchday page for the exact season/round. It validates selected season, round, canonical URL, ten completed matches and twenty populated club tables. It reads pure votes, published classic fantasy votes and goalkeeper conceded goals. Coaches and the provider's no-vote sentinel codes (55/56) are excluded. It does not request protected spreadsheet downloads or use season averages as actual scores.

Scoring uses published fantasy votes, adds the saved profile's goalkeeper clean-sheet bonus, then applies same-role substitutions in P/D/C/A order (with the saved cap and bench priorities) and the defensive modifier from pure votes. The supported scoring profile is the existing Classic default, allowing 0–5 substitutions and custom league metadata/preferences. Other hard-rule profiles are marked unsupported; this does not prevent storing their AI suggestions. FantaMaster teams instead use the public `publicapi.fantamaster.it/ratings/?day=…` feed's `mark` and `fmark`, with `playersstats` providing FantaMaster player IDs for known nonparticipants. Fantacalcio IDs saved with research are never used to match FantaMaster votes. Unique normalized name/club matches identify roster players; ambiguous identities and special no-vote event cases stay pending. The feed's zero mark means no vote, not a zero-point rated appearance. Published fantasy points receive the same saved clean-sheet and pure-vote modifier rules.

Because FantaMaster ratings do not expose a season, the collector anchors them to the dates and current matchday of FantaMaster's own livescores feed, verifies the requested season and ten finished fixtures against the official Serie A calendar, and requires rated coverage for all twenty clubs. Current-round votes must be finalized (FT/F). Older rounds in the verified current season are supported; previous seasons are rejected rather than guessed. Public JSON downloads are bounded, timed out and cached for five minutes. No login or AI call is needed. Results retain their exact provider/source URL. Existing scores from a different provider are shown pending and excluded from rankings until successfully recalculated; failed refreshes retain the stored record. Scoring and refreshing never replace the saved formation or bench.

Unknown identities/votes that affect a starter or its priority replacement stay pending. Unknown unused reserves do not block a score. Stable provider IDs allow absence from a complete vote page to mean no vote; ambiguous names, special S.V. event cases and duplicate real-player identities are not guessed.

A winner or tie is shown among the saved methods when at least two methods have complete results, identical hard rules and the same vote retrieval snapshot. Generation time does not exclude a method, including legacy results marked late.

Two all-time rankings are shown per team, across all archived seasons and matchdays: sum of complete actual fantasy scores (with the count of scored rounds), and number of matchday wins (with the count of eligible comparisons). Every method tied for the highest score earns one win. Incomplete or inconsistent rounds award no wins; single-method rounds still count toward total fantasy points. Scores are already persisted in `actual_result`; rankings are derived server-side from that archive rather than incremented counters. Existing saved scores count immediately. Refreshing votes or replacing a recommendation recalculates standings without double counting. GET and successful POST responses include compact rankings, with no roster/prompt data needed for aggregation.

The votes parser was also checked against a real public matchday page.

## Background AI jobs

Hosted DeepSeek and Kimi suggestions now use `/api/ai-jobs`. The browser submits only a request UUID, team/model and expected research/roster context; the server loads the saved roster and builds the same shared prompt. A PostgreSQL job is accepted before returning HTTP 202. Vercel `waitUntil` keeps generation running after that response, independently of the phone connection. An active-job unique index allows only one running generation per team, even across models/devices; repeated request IDs are idempotent. Reconnecting performs status reads, never automatic paid generation retries.

The worker validates the model's response and merges into the latest workspace revision. Changed roster/rules/research, removed teams or a newer recommendation prevent application. Unrelated workspace edits are preserved through bounded database-only conflict retries. Workspace, method/day archive and completed job status commit in the same SQL statement. Expired workers cannot commit. Completed/failed jobs discard their roster snapshot. Prompts and credentials are never returned from status endpoints.

The app shows wall-clock elapsed time and an indeterminate loading bar, with no fabricated percentage. It resumes status checks on visibility/connection changes and reopening. Only the request UUID is kept locally to recover a lost start response. The final recommendation and costs are stored on the server and restored to the pitch and Confronto. A failed result reload has a separate Ricarica risultato action that does not generate again. Once accepted, a server generation is not cancelled by closing the page; the browser's cancel action remains available for existing local/research/follow-up operations.

These are bounded background jobs, not a durable retry queue: the Vercel function and job lease expire after five minutes, with a 260-second upstream timeout reserving time for validation/database saving. Provider failures, invalid responses and interrupted/expired workers retain the previous choice and show an error without automatic provider retries. A request may consume provider credits even when it fails. Statistical engine, manual modes and follow-up requests retain their existing execution paths.

Validation includes client cancellation, tab closure/reopening, elapsed-time recovery, simultaneous starts/idempotency, changed context, expiry, malformed responses, provider timeout, atomic saving and unrelated revision conflicts, using disposable PGlite databases and fake AI responses.
